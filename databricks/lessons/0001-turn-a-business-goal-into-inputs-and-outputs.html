Lesson 0001 · About 8 minutes

Turn a business goal into inputs and outputs

Your first exam move is not choosing a model. It is stating what the system receives, what facts or permissions it needs, and what observable result it must produce.

Guide objective, quoted exactly:
Translate business use case goals into a description of the desired inputs and outputs for the AI pipeline.

The core idea

Databricks tells builders to clarify the input types, intended responses, required context, quality criteria, production constraints, and failure handling before implementation. That work identifies the data sources and tools the agent needs. Official source.

For exam scenarios, split the requirement into two sides:

Inputs
User request, required fields, identity, conversation context, knowledge sources, and authorized tool parameters.
Outputs
User-visible response, required format or citations, external action or artifact, and a safe fallback.

Do not confuse an implementation component with an input or output. “Use an LLM” is not an output. “Use AI Search” is not an input. Those choices come after the contract is clear.

Worked example

A customer asks, “Can you return my last order?” The application must check the live order, apply the current return policy, create the return when eligible, and provide a shipping label. Otherwise, it must explain why it cannot proceed.

This mirrors the return workflow in Databricks' current agent design documentation. The documented flow looks up the order, consults the policy, checks eligibility, performs the return, generates a label, and responds. Official source.

User input
Return request and authenticated customer identity. Ask for an order identifier if “last order” cannot be resolved safely.
Knowledge input
Live order record plus the current return-policy document.
Action input
Eligible order identifier and authority to initiate a return.
Response output
Eligibility result and explanation. Include the policy basis when the interface requires it.
Action output
Created return, return identifier, and shipping label when eligible.
Fallback
Request missing information, refuse an unauthorized action, or explain that the return is ineligible.

Why this changes the architecture

A fixed, well-defined sequence can use a deterministic chain. When the system must decide which tools to call for varied requests, a single-agent system can make that choice dynamically. Databricks recommends choosing the simplest viable design and adding complexity only when the requirements need it. Official source.

Retrieval practice

An employee asks, “Can I take five days off next month?” The assistant must use the employee's live leave balance and the company's current leave-policy documents. It cannot approve leave. It should answer with remaining balance, whether the request fits policy, and what the employee must do next.

Write the contract from memory. Keep products and implementation details out of it.

Check a model answer
User input
Authenticated employee identity, requested dates, and requested duration.
Knowledge input
Live leave balance and current leave-policy documents.
Action input
None. The scenario does not authorize approval or any other state change.
Response output
Remaining balance, policy fit, and the next step for submitting the request.
Action output
None.
Fallback
Ask for missing dates or explain that balance or policy information could not be retrieved.
Self-check. You have the skill when you can explain why the leave balance is a live data input, the policy is a knowledge input, and approval is absent from the output contract.
