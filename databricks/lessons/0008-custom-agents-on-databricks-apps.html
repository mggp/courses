1. What runs where?

A Databricks app is a containerized web service on Databricks serverless infrastructure, with its own runtime and identity. It can call other Databricks services. For our agent, the app hosts orchestration code; an LLM API handles generation, and a retriever or tool accesses data. Deploying the app does not move those remote services into its container. 3. Know which file controls what

Agent source
Handlers, prompts, adapters, and tool logic. Migration moves source and supporting artifacts into the app project and updates their paths. Source layout.
databricks.yml
The Declarative Automation Bundle defines app resources and deployment settings. Use it to version and deploy the application configuration. Apps and bundles.
app.yaml
Defines runtime settings such as the start command and environment variables. The agent guide also shows inline app config in the bundle. Follow your template's configuration structure. App execution; inline configuration example.
Dependency files
requirements.txt takes precedence and selects pip. Without it, pyproject.toml plus uv.lock selects uv. Declare all packages for a uv-based app; those apps have no preinstalled Python libraries. Install rules.

Commit the lockfile and constrain the Python interpreter to a tested version. A package lock alone does not select the interpreter. For the current migration template, Databricks recommends requires-python = ">=3.12,<3.13". Reproducible deployment.

4. Separate entry permission from data identity

CAN USE lets someone run and interact with the app. It does not answer whose credentials the agent uses for its next data call. App permissions; Authorization models.

RequirementIdentity to use
All callers may read the same support corpus.App authorization. Databricks creates a dedicated service principal; grant it the required resource access.
Each salesperson must see only their permitted rows.User authorization. Use the forwarded caller identity so their existing Unity Catalog policies apply.
Shared trace logging plus private user data.Combine them. Write traces as the app, query restricted data as the user.

All three choices follow the documented authorization comparison.

For user authorization, both API scopes and the user's resource permissions must allow the call. A sql scope permits the relevant API usage; it does not grant SELECT on a table. Use the template's get_user_workspace_client() helper during request handling, when the forwarded token exists. Check the helper's import path in your template: Databricks examples use both agent_server.utils and databricks_app.utils. Scopes; Request-time client.

Test the actual identity. The agent authentication guide documents a fallback to the app service principal when the forwarded token is absent. Test its whoami diagnostic with two users. For user-restricted operations, treat an unexpected app identity as a failed authorization test, even if the answer looks correct. Identity verification.

5. Resource access still needs configuration

App resources connect code to existing services and grant the app identity access. For example, a SQL warehouse grant covers query compute, while the tables need their own grants. An environment variable containing a warehouse ID is configuration, not permission. Resource declarations; Warehouse and table access.

MCP connects the agent to tools, but the caller still needs access to the resources behind those tools. For app authorization, declare the required indexes, functions, or other supported resources under resources.apps.<app>.resources. A pure local calculation tool needs no external resource grant. MCP access; Local tools.

Current LLM routing caveat

The latest guidance routes agent LLM calls through Unity Gateway. Where enforcement is enabled, legacy pay-per-token endpoints are disabled. Configure the appropriate model API and grant the calling identity EXECUTE, plus catalog and schema usage. Adding the old serving-endpoint resource alone does not complete that migration. This is a downstream LLM access issue, separate from deploying the agent app. Unity Gateway migration and Apps limitations.

6. Release code, then verify behavior

databricks bundle validate
databricks bundle deploy
databricks bundle run YOUR_APP_RESOURCE_KEY

Use the key under resources.apps for the final command. Validation checks configuration. Deployment uploads source and configures resources; running the app starts or restarts it with that code. Uploading a new version alone is insufficient. Bundle workflow.

For a release, check tool behavior and user access, then evaluate answer quality on a fixed dataset. MLflow separates traces, assessments, evaluation runs, and application versions. A healthy HTTP response is only one piece of that evidence. MLflow quality data.

Keep three kinds of state distinct. A request's message history provides conversation context. The template's optional Lakebase-backed chat history persists conversations across sessions; its default in-memory history does not. Agent working state needs its own deliberate persistence design. A trace is an execution record, not a memory mechanism that automatically supplies the next prompt. Chat persistence; Trace semantics.

7. Lab: add a tool and inspect the call

Use a development workspace with Apps enabled and access to an approved LLM. Creating and querying the template uses app and model resources. The task is complete when a trace shows your custom tool executing in the deployed app.

  1. Create an app through + New → App → Agents → Custom Agent (OpenAI SDK). Create or select the MLflow experiment during setup. Open its chat UI, then use the app page's source-sync command to obtain the project locally. Template setup.
  2. In the module that constructs the agent, add this original teaching tool and append it to the agent's existing tools list. Preserve its configured model, clients, and MCP connections. The SDK decorator pattern is documented by Databricks. Function tools.
from agents import function_tool

def count_words(text: str) -> int:
    """Count whitespace-separated words in the supplied text."""
    return len(text.split())

assert count_words("  deploy   then run  ") == 3
assert count_words("   ") == 0

word_count = function_tool(count_words)
# Add word_count to the existing Agent(..., tools=[...]) list.
# Instruction to add to the agent:
# "For word-count requests, call count_words and return its result."
  1. Test locally using the template's uv run quickstart and uv run start-app commands. Ask it to count the words in deploy then run. Expected tool result: 3. Local execution.
  2. Because the UI already created the app, bind it before the first bundle deployment: databricks bundle deployment bind YOUR_APP_RESOURCE_KEY YOUR_APP_NAME. Then run the three release commands above. Binding avoids a duplicate-name failure. Existing-app binding.
  3. Repeat the request in the deployed chat UI. Inspect its MLflow trace for the tool arguments and result. Seeing the number 3 alone is insufficient, since the LLM might have calculated it without calling the tool. The experiment needs app access to record traces. Experiment access; Trace evidence.

For a client-side query, use an OAuth-configured Databricks profile and installed databricks-sdk and databricks-openai packages. The apps/ prefix selects the app; stream=True selects its streaming path. Apps requires OAuth rather than a PAT. Query API.

from databricks.sdk import WorkspaceClient
from databricks_openai import DatabricksOpenAI

client = DatabricksOpenAI(
    workspace_client=WorkspaceClient(profile="YOUR_OAUTH_PROFILE")
)
response = client.responses.create(
    model="apps/YOUR_APP_NAME",
    input=[{
        "role": "user",
        "content": "Use count_words on: deploy then run",
    }],
)
print(response.output_text)

Optional identity exercise: follow the official whoami check, then test an allowed and denied data request with two users. Do not infer per-user enforcement from your local developer session.

8. Diagnose the failure

Give a cause and a correction before opening each answer.

A. Your Git revision and workspace files contain a new tool, but the app behaves exactly as before. Bundle deployment succeeded.
Reveal A

Check whether the app was restarted through bundle run. Bundle deployment uploads files and configures resources; it does not start the updated app. Deployment sequence.

B. Two users with different table access receive the same privileged results. Both have permission to use the app.
Reveal B

Inspect the downstream identity. App authorization uses shared service-principal grants. For user-specific results, use user authorization, suitable scopes, and request-time credentials; test for the documented fallback. Identity choice; Fallback check.

C. CI committed uv.lock, but the app build resolves packages through pip.
Reveal C

Check for requirements.txt. It takes precedence. For the uv path, retain the project file and lockfile and remove the obsolete requirements file after confirming all needed dependencies are declared. Installer selection.

D. A colleague sees a Logged Model associated with the app's traces and assumes its ID identifies the deployed model artifact.
Reveal D

Inspect what that Logged Model represents. It can be a metadata record linked to an external Git revision. Its existence does not establish that application source was packaged inside it or deployed through the model registry. Application-version tracking.

E. The app's chat UI shows yesterday's conversation, so the team assumes the agent can recover an unfinished tool workflow automatically.
Reveal E

Persisted chat messages establish history storage. They do not by themselves establish workflow-state recovery. Inspect how the next request reconstructs agent state and which store holds unfinished work. This distinction follows from the chat template's documented persistence scope. Chat history.
