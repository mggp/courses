CI/CD for AI workflows, prompts, and scorers

An AI release is not one artifact. Code, Databricks resources, prompts, retrieval data, scoring policy, and evaluation evidence can change on different schedules. The useful skill is knowing what to version, what to promote, and what to test before one environment can point at the next candidate. Exam objectives; Databricks CI/CD; MLflow Prompt Registry.

Your win. Given a development, staging, and production scenario, choose the release mechanism for each artifact. Then design a quality gate that can reject a prompt, scorer, or agent change without confusing source control, deployment, indexing, and evaluation.

The central distinction. A Git merge promotes source. A bundle deployment promotes Databricks code and resource definitions. An alias reassignment promotes a prompt version. An index sync promotes changed retrieval data into the searchable index. A pinned scorer version fixes the quality policy used by the gate. None substitutes for the others.

A release has two loops

For this lesson, continuous integration means that every candidate change runs automated checks. Continuous delivery means the passing candidate is ready for a controlled release, which may still require approval. The exam's “gated release process” is this second shape: automation proves readiness, then an authorized promotion changes the production reference. The Databricks CI/CD overview defines the broader practice as short, frequent development and delivery cycles built around automated build, test, deployment, and monitoring. Source.

The software loop handles code and infrastructure. Store source in Git, develop unit tests, validate the bundle, deploy it to an isolated target, run integration tests, and then deploy the approved revision to production. Databricks names version, code, build, deploy, test, run, and monitor as the common CI/CD flow, and recommends Declarative Automation Bundles for deployment. Source.

The quality loop handles probabilistic behavior. Trace the application, build a representative evaluation dataset, run the candidate with fixed scorers, compare it with the baseline, and continue monitoring production. MLflow 3 supports the same judges and scorers in development and production, and it can run evaluation as part of a release process. Source.

Keep both loops. A unit test can prove that the retriever receives the right filter, but it cannot prove that the final answer is sufficiently grounded. An LLM judge can score groundedness, but it should not replace an exact assertion that a forbidden tool was never called. Databricks describes GenAI output as non-deterministic and supports built-in and custom scorers for qualities that are not captured by exact software assertions. Source.

Prompt lifecycle on Databricks

  1. Register. Give the prompt a three-level Unity Catalog name and call mlflow.genai.register_prompt(). Registering again under the same name creates another version. Commit messages and tags record why it changed. Source.
  2. Do not edit in place. Prompt versions are immutable. An edit creates a new version, which preserves history and supports rollback. Source.
  3. Test a fixed version. Load the candidate by version number while evaluating it. Use the same dataset and scorers for the candidate and baseline so the comparison measures the prompt change rather than a changed test. Source.
  4. Promote by alias. Assign dev, staging, or production to an approved version. A deployed application can load prompts:/catalog.schema.name@production, so moving the alias can update its prompt without a code redeployment. Source.
  5. Keep rollback cheap. Before moving production, preserve the current version under an alias such as production-previous. Rollback is another alias reassignment. Databricks includes this pattern in its deployed-prompt guide. Source.
  6. Track the prompt with the app. When an application has an active MLflow model, loading a registry prompt creates lineage between the prompt version and application version. The MLflow LoggedModel acts as the application-version record and can link to an external Git commit. Source.

Current product status. The Databricks documentation marks MLflow Prompt Registry on Databricks as Beta. Treat it as the correct current mechanism for this exam objective, but check Preview availability and the documented Unity Catalog privileges before planning a production rollout. Source.

Release scorers before they judge releases

A scorer defines what “good enough” means. Changing its instructions, judge model, output type, threshold, or aggregation can change which prompts pass even when the application does not change. Treat the complete quality policy as a release unit: scorer definition, judge model, evaluation dataset version, acceptance threshold, and aggregation rule.

MLflow stores supported registered scorers by experiment and name. The first registration creates version 1; registering another scorer with the same name creates the next version. Existing versions remain available, and get_scorer(version=...) loads a fixed definition. Pin that version in regression tests and promotion workflows. Loading the latest version is suitable only when the workflow should adopt scorer changes automatically. Source.

Do not confuse a definition change with Scorer.update(). Databricks documents update() for an active production scorer's sampling configuration, including sample rate and trace filter. To change judge instructions, model, or output type, register a new scorer version. Source.

Qualify the new ruler

  1. Keep the incumbent scorer pinned as the current release gate.
  2. Create the candidate as a new scorer version rather than replacing the incumbent. Source.
  3. Run both versions over the same expert-labeled scorer-validation set. Examine agreement with the experts, especially false passes and false failures. Databricks supports expert corrections and alignment of built-in and custom judges to human feedback. Source.
  4. Replay both versions over the same historical production traces. Databricks backfill can apply new or updated scorers to earlier traces. Source.
  5. Approve the scorer on its own. Then change the release configuration to pin the new version. Do not silently switch scorer versions inside a prompt comparison.
  6. For production monitoring, run an overlap only with distinct assessment names, then stop the old scorer and start the approved replacement. Stopping keeps the registration; deleting removes it. Production scorer lifecycle management is currently Beta. Source.

Use the four-way comparison

PromptScorerQuestion answered
CurrentCurrentWhat is the stable baseline?
CandidateCurrentDid the prompt improve under the already-approved policy? This is the prompt-promotion gate.
CurrentCandidateHow much did changing the scorer move the measurements?
CandidateCandidateWhat results should you expect after both changes are released?

Never move the ruler during the race. Promote the candidate prompt against the incumbent scorer. Qualify and promote the candidate scorer separately. If both change in one comparison, an apparent improvement might only mean the scorer became more permissive.

Pin a scorer in the gate

from mlflow.genai import get_scorer

release_scorer = get_scorer(
    name="support_release_quality",
    experiment_id=experiment_id,
    version=3,  # fixed until scorer version 4 is approved
)

results = mlflow.genai.evaluate(
    data=versioned_eval_dataset,
    predict_fn=candidate_app,
    scorers=[release_scorer],
)

MLflow scorer version histories currently support custom LLM judges and built-in judges. The scorer-versioning documentation does not list code-based scorers or Guidelines judges as supported; it directs Guidelines judge versioning to MLflow Prompt Registry. Keep code-based scorer source in Git and tie each evaluation result to its code revision and registered production name. Source.

Unlike Prompt Registry, the documented scorer workflow has no environment aliases. The practical promotion mechanism is an explicit version in the release configuration. Record that version with every evaluation result so a quality time series does not silently change meaning.

AI Search belongs in the release plan

A prompt may expect fields or document content that the current index does not contain. For a Delta Sync index in Continuous mode, changes to the source table or view flow into the index automatically. For Triggered mode, the pipeline must call the sync operation, such as index.sync(), and wait until the index is ready before running retrieval tests. Standard endpoints process changed data incrementally in both modes; storage-optimized endpoints support only Triggered sync and partially rebuild on each sync. Source.

The release order follows the dependency: update the governed source, sync the candidate index, run retrieval tests, run end-to-end evaluation, then promote the prompt or application. This ordering is a practical inference from the documented index update and evaluation mechanisms, not a Databricks-mandated pipeline shape.

Bundles, aliases, and Terraform are not rivals

  • Use a Declarative Automation Bundle when application code, tests, jobs, pipelines, Model Serving endpoints, MLflow experiments, or registered models must move together through targets. Databricks recommends bundles for CI/CD. Source.
  • Use Prompt Registry aliases when the release unit is a prompt and the application should select an approved version without changing code. Source.
  • Use the Databricks Terraform provider for workspace or account infrastructure when Terraform is the right infrastructure-as-code boundary. Databricks lists Terraform separately from bundles and points to developer-tool use cases for the choice. Source.
  • Use Git folders alone only when you need source-controlled files and lack an external CI/CD pipeline. Git folders do not source-control job and pipeline configuration, which makes them weaker for multi-environment deployment. Source.

Authentication and isolation

Define separate bundle targets for development, staging, and production settings. Bundle targets can override workspace, variables, resources, permissions, and run identity. Development and production modes apply different defaults, including paused development schedules and production branch validation. Targets; deployment modes.

Do not infer a third bundle mode named staging. Target names are user-defined, but the documented mode values are development and production. A team can name a target staging and configure it for pre-production behavior. Source.

For CI/CD authentication, Databricks strongly recommends workload identity federation where possible. The automation authenticates as a service principal using an identity-provider token, avoiding stored Databricks secrets. Source.

Runnable prompt-promotion exercise

Run this in a Databricks notebook after replacing main.genai with a Unity Catalog catalog and schema you can use. The Prompt Registry documentation lists MLflow 3.1 or later and Unity Catalog privileges including CREATE FUNCTION, EXECUTE, and MANAGE as prerequisites. Source.

%pip install --upgrade "mlflow[databricks]>=3.14.0"
dbutils.library.restartPython()

import mlflow

mlflow.set_tracking_uri("databricks")
mlflow.set_registry_uri("databricks-uc")

name = "main.genai.release_lesson_prompt"  # change this

v1 = mlflow.genai.register_prompt(
    name=name,
    template="Answer the question in one sentence: {{question}}",
    commit_message="Baseline one-sentence answer",
)

v2 = mlflow.genai.register_prompt(
    name=name,
    template=(
        "Answer using only the supplied context. "
        "If the context is insufficient, say you do not know.\n"
        "Context: {{context}}\nQuestion: {{question}}"
    ),
    commit_message="Require grounding and abstention",
)

# Development points to the candidate.
mlflow.genai.set_prompt_alias(name, "dev", v2.version)

# A release test should load the fixed version, not a moving alias.
candidate = mlflow.genai.load_prompt(f"prompts:/{name}/{v2.version}")
rendered = candidate.format(
    context="Paris is the capital of France.",
    question="What is the capital of France?",
)
assert "Paris" in rendered

# After evaluation passes, move the same tested version through the gates.
mlflow.genai.set_prompt_alias(name, "staging", v2.version)
mlflow.genai.set_prompt_alias(name, "production", v2.version)

production = mlflow.genai.load_prompt(f"prompts:/{name}@production")
assert production.version == v2.version
print(f"Production now uses prompt version {production.version}")

# Rollback is an alias move. In a real release, preserve the former
# production version before promotion under a production-previous alias.
mlflow.genai.set_prompt_alias(name, "production", v1.version)

This exercise verifies registry mechanics, not response quality. A real gate must run both prompt versions against the same evaluation dataset and scorers before moving production. Source.

Common mistakes

  1. Treating a mutable prompt alias as a version. A version is immutable; an alias is a movable name that points to one version. Source.
  2. Evaluating @staging and later assuming it still identifies the tested content. Record and test the resolved version number for reproducibility. The registry supports loading both aliases and fixed versions. Aliases; fixed versions.
  3. Promoting a prompt because its text diff looks sensible. A text diff shows wording changes; Databricks says to run both versions on the same dataset and judges to compare output quality. Source.
  4. Testing only the final answer. A failure might come from query understanding, retrieval, prompt augmentation, generation, or post-processing. Test the changed component and then the whole path. Source.
  5. Changing source documents without confirming index freshness before evaluation. Triggered Delta Sync indexes require an explicit sync. Source.
  6. Using one person's credentials in unattended production deployment. Databricks recommends service principals and workload identity federation for CI/CD. Source.
  7. Assuming a successful bundle deployment proves agent quality. Deployment and evaluation are separate gates in the documented lifecycle. CI/CD; GenAI evaluation.
  8. Loading the latest scorer in a reproducible release gate. Pin the approved scorer version and update that pin only after the scorer passes its own review. Source.
  9. Changing a prompt and its scorer together, then crediting the prompt for a higher score. Keep the incumbent scorer as the prompt gate and use the four-way comparison to isolate both effects.
  10. Calling Scorer.update() a rubric update. It changes sampling configuration, not judge instructions or model. Source.
