Guardrails versus observability

A service policy makes a decision while a governed AI-service interaction is in flight. MLflow Tracing records an agent's execution so you can inspect it and measure quality. In an exam scenario, ask whether the requirement is to stop this interaction now or learn what happened. Policy source; tracing source.

How a governed call proceeds

Unity Catalog privileges first determine whether the principal can call the service. An attached service policy then inspects the request at ON CALL. If it allows the call, the service runs. The policy can inspect the result at ON RESULT before the caller sees it. A DENY stops the interaction at either point. Grants and policies; evaluation points.

A policy DENY returns an HTTP 200 assistant turn with a top-level databricks_service_policy object and a block reason. A successful HTTP status therefore does not prove that the model answered. Source.

Databricks provides built-in policies for unsafe content, jailbreak attempts, hallucinated responses, and sensitive-data detection. A custom policy is a Unity Catalog SQL function over an interaction event. Built-in model-backed checks can make non-deterministic judgments; the sensitive-data detector is pattern-based and can redact matched values on model services. Built-in policies; custom functions.

Availability. Service policies are beta and require an account admin to enable the Unity Gateway beta preview. A policy in Log mode records the decision it would make but does not block. Source.

Where tracing fits

An MLflow trace represents one complete agent execution. Child spans can show the retriever lookup, model call, and tool invocation, with their inputs, outputs, timing, and errors. Tracing gives you evidence to debug an answer; it does not return a service-policy decision. Source.

For continuous quality measurement, MLflow production monitoring runs built-in or custom scorers on a configurable sample of incoming traces and attaches feedback to evaluated traces. Instrumentation and scorers are separate setup steps. Source.

For endpoint request volume, token use, or latency across Unity Gateway services, use system.ai_gateway.usage. For model-service request and response payloads, enable inference tables. These records answer different questions from an application's multi-step MLflow trace. Source.

Common traps

  1. Using a trace as a blocking guardrail. A trace records execution; a service policy returns the runtime decision. Tracing; policy.
  2. Using a service policy in place of access control. The principal still needs Unity Catalog privileges. Source.
  3. Assuming the protected model service logs every blocked request. ON CALL DENY means the model is never invoked, so its inference table may have no row for the block. The evaluator service's inference table can record model-backed verdicts when enabled. Source.
  4. Treating Log mode as enforcement. It records a would-be DENY and lets the request proceed. Source.
  5. Assuming built-in checks see the whole conversation. By default they inspect one extracted message; model-service input policies can inspect a configured window of recent turns. Source.

Run a trace in a Databricks notebook

Replace the experiment path with one you can create. This function needs no model endpoint. It shows what tracing records, without claiming to test a service policy. The decorator and experiment workflow follow the trace UI guide and manual tracing guide.

import mlflow

mlflow.set_tracking_uri("databricks")
mlflow.set_experiment("/Users/<your-email>/guardrails-vs-tracing")

@mlflow.trace
def reply(prompt: str) -> str:
    return f"Draft answer for: {prompt}"

reply("Tell me about Project Aurora")

Open your experiment's Traces tab and inspect the input and output. The phrase appears in a trace because this code only records the function call. To see enforcement in a workspace with the beta enabled, follow the official model-service guardrail tutorial, which attaches a custom ON CALL policy and verifies a blocked prompt in the playground.
