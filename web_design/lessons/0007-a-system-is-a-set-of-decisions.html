Lesson 7 · about 10 minutes

A system is a set of decisions

A component library gives you parts. A design system gives those parts—and the choices around them—a shared reason, behavior, and boundary.

Your win: decide whether a repeated UI decision belongs in a foundation, component, pattern, or nowhere yet.

Not a shelf of components

Imagine three familiar buttons that all look polished, but only one signals loading, another changes its wording to “Done” after a save, and the third silently fails. The mismatch is not merely visual. Each button makes a different promise about the same action.

A design system makes the shared decision explicit: what a primary action looks like, which states it needs, how it receives focus, and how the outcome is communicated. Code can implement that decision, but code alone is not the system.

FoundationsShared meanings: type roles, spacing steps, semantic colour.
ComponentsReusable parts with visual, behavioral, and accessibility contracts.
PatternsCompositions that solve a recurring user task.
GovernanceEvidence and rules for changing the shared decisions.

Think of this as an API with human consequences. The API is useful because its contract is predictable; design-system contracts are useful because people can predict an interface before they experiment with it.

System map lab

Put the decision at the right level

Classify each decision by the kind of consistency it protects. There is one correct level for each.

“Danger” always uses a named semantic colour, whether it appears in a button, notice, or form error.

The primary Button documents its default, disabled, loading, and focus states, as well as its native semantic element.

Deleting an item asks for confirmation, names what will be removed, and returns a clear result.

A request for “one more button style” needs a repeated user need, an accessibility check, and an owner before becoming a variant.

Choose a level. The feedback will explain the boundary.

Do not systematize a one-off

For a personal project, start by capturing only decisions that repeat or are expensive to get wrong. A token for danger, a button contract, and a form-error pattern may be enough. A bespoke “violet compact button” used once is an exception until you can name a recurring user need that requires it.

Make an exception earn its abstraction

GOV.UK’s contribution criteria require proposed additions to be useful, unique, usable, consistent, and versatile. Borrow the spirit, not the bureaucracy: before adding a variant, ask whether it solves a repeated need, reuses existing rules where possible, and remains accessible across its real contexts.

Write the critique

“These three save actions share a label but not an outcome contract. Define one Button state model—idle, working, succeeded, failed—then apply it consistently wherever the action saves data.”

Do this on one of your pages

  1. Choose a repeated decision: an action, an error, a heading role, or an empty state.
  2. Write its intent and its observable contract: cues, states, behavior, and feedback.
  3. Find two instances. Mark any difference that has no different user need.
  4. Keep a true one-off local; turn a repeated, justified decision into a documented rule.
