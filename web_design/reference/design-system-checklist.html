Design-system seed checklist

A small, evidence-backed set of decisions that keeps a personal project coherent without inventing a platform team.

Start with the smallest useful system

1. Repeated decision
What appears in more than one place, or will be costly to change separately?
2. Intent
Name the job, not its pixels: “primary action,” “error message,” “content heading.”
3. Rule
State the invariant: one primary action per local context; destructive actions use a semantic danger treatment.
4. Contract
Specify visible states, behavior, semantics, keyboard use, and feedback.
5. Evidence
Record the user need, accessibility constraint, or observed failure that justifies the rule.
6. Exception
Allow it only for a named context. Decide whether it is a one-off, a variant, or a new pattern.

Classify before you build

When you see…Capture it as…
A shared meaning such as success, danger, or a spacing stepFoundation / token
A reusable UI part with a stable interface and statesComponent
Several parts solving a recurring user taskPattern
A new requirement that matters only onceLocal decision; do not generalize yet

Review a proposed addition

  1. What user task recurs, and in which contexts?
  2. Can an existing rule, component, or pattern meet it without concealing a meaningful difference?
  3. Which accessibility and interaction states must remain true?
  4. What evidence supports it, and who owns the decision?

“This is a local styling exception, not yet a Button variant: it appears once and has no distinct user task or interaction contract. Keep it local until repetition and evidence justify a rule.”
