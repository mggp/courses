Not every AI problem is RAG

The same text vectors can return evidence or predict a label. The difference is the question, the data, and what counts as an error.

~40 minutes  ·  Python  ·  lesson 7  ·  glossary

Why this lesson

Your fintech short-list has always contained two different problems. KYC audit and document Q&A ask, "what do the sources say?" — the RAG spine you finished in lesson 7. Fraud detection, loan underwriting, and credit risk ask, "which predefined outcome best fits this case?" That is a prediction problem. This lesson begins that second toolkit with harmless fictional support-ticket routing, not a credit or fraud decision. The mechanics transfer; the production claim does not.

Same vectors, different contract

You already know one use for vectors: compare a question with documents and return the closest sources. Classification starts with the same text-to-numbers step, but adds labeled examples and changes the output contract.

Input texta question or ticket → TF-IDF vectorword-weight features → Retrieverank source texts to inspect
Input texta ticket to route → TF-IDF vectorword-weight features → Classifychoose from fixed labels

Retrieval needs a corpus but no labels. It returns evidence: arbitrary chunks a person or LLM can read. Classification needs examples already labelled billing, access, or lesson. It learns associations from text to that fixed vocabulary and returns one label plus scores. The output is a decision candidate, not a source trail.

TF-IDF is the bridge. The scikit-learn docs describe TF-IDF as a term-weighting scheme born in information retrieval that is also useful for document classification. Same representation; different objective. That is why this is the right first prediction lesson after RAG.

A probability is not an action

A classifier estimates something like P(label | ticket). The product still has to decide what to do with that score: route automatically, ask for human review, or take another action. The decision threshold is policy, not model truth. Scikit-learn's threshold guide makes the split explicit: probability estimation is a statistical problem; choosing an action is a separate decision problem.

That distinction is why this lesson has an abstain path. A ticket can mention both billing and account access. Forcing it into one label merely because one score is fractionally larger hides ambiguity. At a higher threshold the right output is needs_review.

Build it

In exercises/lesson0008/, tickets.json is a tiny, fictional, labelled Lingua support dataset: 24 training tickets and 9 held-out tickets across three routing labels. classify.py fits one TfidfVectorizer, then uses it two ways: cosine similarity for retrieval and logistic regression for classification. The test split is fixed so the run is reproducible.

  1. Run uv sync, then uv run classify.py. The script prints the two contracts side by side: retrieved source tickets first, then classifier evaluation and an action decision.
  2. Read retrieval. For "I was charged twice for premium and need a refund", it returns three billing tickets with cosine similarities. It does not decide what the new ticket is; it hands you evidence to inspect. Labels are incidental here.
  3. Read classification. The same vectorizer now trains a logistic regression on the 24 labelled tickets and scores the 9 never-seen test tickets. You should see macro F1 = 1.00 and a diagonal confusion matrix. Do not celebrate: that is a tiny, stylized teaching dataset, not validation of a real product. The win is that the score came from held-out labels, not from how plausible the predictions looked.
  4. Read the ambiguous ticket. "My card was charged twice and I cannot log in after changing phones" gets access=0.40, billing=0.35, lesson=0.25. At the default 0.60 threshold, the action is needs_review. That is the honest answer: this input contains two issues and the classifier is unsure.
  5. Change policy, not the model. Run uv run classify.py --threshold 0.30. The probabilities stay identical, but the action becomes access. You changed the cost policy, not what the model learned. A 0.5 default is a library convention, never a business justification.
  6. Carry the boundary to fintech. A fraud or underwriting classifier needs representative labelled history, error costs, validation, calibration, fairness analysis, governance, and human review. This toy teaches only the first question: are you retrieving evidence, or predicting from a fixed label set?

Stuck? Ask your teacher

Why macro F1 rather than accuracy, what logistic regression learned from the vectors, why a threshold cannot be tuned on the test set, how an LLM classifier changes the interface but not the evaluation contract, or why credit underwriting needs a much stricter process — ask.
