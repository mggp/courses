Safety is a control plane

A prompt can suggest behavior. A control plane decides what the system is allowed to trust, return, execute, record, and escalate.

~40 minutes  ·  Python  ·  lesson 9  ·  roadmap  ·  glossary

Why this lesson

Your diagnostic answer to financial-RAG safety had the right instinct — abstain when evidence is missing — but only one control. This lesson turns that instinct into a layered answer: authoritative data, retrieval and provenance, structured output, claim checks, tool authorization, auditability, and human escalation. It also closes the missing sampling concept: temperature and top_p control variation; they do not make an answer safe or true.

Guardrails are not a prompt sentence

“Answer only from the context” is a useful instruction. It is not an enforcement mechanism. The model can still produce an unsupported claim, cite the wrong chunk, request an unsafe tool, or return malformed data. A guardrail is a control that constrains, checks, or routes a system at a specific boundary. A control plane is the set of policies, checks, approvals, measurements, and escalation paths that govern the AI data plane.

Guardrails are one part of the control plane

Your inference is right: runtime guardrails belong in the control plane. But the control plane is broader than the guards themselves. It decides the intended behavior, supplies the rules and versions, observes what happened, and changes the system when evidence says the current behavior is unsafe, ineffective, or too expensive.

  • Policy and configuration: risk limits, schemas, tool permissions, tenant scope, prompts, model versions, retrieval indexes, thresholds, and feature flags.
  • Decision and routing: guardrails, retries, fallbacks, abstention, human approval, rate limits, and kill switches.
  • Identity and governance: caller identity, ownership, change review, data retention, audit records, and incident handling.
  • Measurement and feedback: telemetry, evaluations, alerts, dashboards, and the actions triggered by those signals.

The data plane is the work being governed: retrieve documents, run inference, call a tool, transform the result, and return an answer. The control plane does not have to be a separate service, but its responsibilities should be identifiable rather than hidden inside the model prompt.

How measurements influence the control plane

A measurement is not automatically a control. A dashboard that displays unsupported-claim rate is observability. It becomes part of the control plane when a defined threshold causes a decision or change:

  • Per request: a failed faithfulness score routes this answer to abstention or human review.
  • During operation: a spike in authorization denials or latency triggers an alert, tighter limits, or a fallback.
  • Between releases: evaluation results change a threshold, prompt, retriever, model version, rollout percentage, or rollback decision.
  • After incidents: false accepts, false rejects, human overrides, and near misses reveal that a policy or detector needs recalibration.

The feedback loop

observe → measure → compare with a limit → decide → change or route → observe again. For example, if an evaluation set shows that a faithfulness threshold misses too many unsupported claims, the control plane can raise the threshold, require human review, change the checker, or roll back the release. That is why measurements influence the control plane: they are evidence for policy and operational decisions, not merely reports after the fact.

Three verbs, made concrete

These are useful engineering categories, not a universal standards taxonomy. Ask what the mechanism does, where it runs, and what happens when it fails:

  • Constrain narrows the set of outputs or actions that are allowed. An enum in a schema, an allowlist of tools, a tenant boundary, or a maximum iteration count constrains the system. A prompt saying “do not do X” is only a soft constraint unless something outside the model enforces it.
  • Check evaluates a proposed input, output, claim, or action against a rule or piece of evidence. It answers “does this satisfy the condition?” A schema validator, a faithfulness check, and a permission check are all checks, although they check different properties.
  • Route chooses what happens next based on the result: proceed, retry, repair, use a fallback, refuse, or send the case to a human. needs_review is a route, not a vague feeling.

The timeline is usually constrain → propose → check → route → execute or abstain. A single mechanism can occupy more than one position: structured output can constrain generation and then be checked by a validator.

So: are these guardrails?

  • Schema validation: yes, when it is a runtime gate that rejects malformed output or routes it to repair/human review. A schema only checks shape; it does not prove the claim is true.
  • Faithfulness check: yes, when it runs on the live answer and blocks, rewrites, or escalates unsupported claims. When you run faithfulness offline to compare model versions, it is an evaluation metric, not a runtime guardrail. Same check; different role.
  • Tool authorization: yes — this is a canonical authorization guardrail. The allowlist, identity, tenant scope, argument validation, and human approval must live outside the model. The model's request is not permission.

Mostly deterministic, but not necessarily certain

It is fair to say that guardrail enforcement is often deterministic: once a policy receives a normalized result, it can apply a fixed rule such as if tool_not_allowed: deny or if schema_invalid: abstain. The same inputs and policy should produce the same route. That is a valuable property for authorization, schema gates, spending limits, tenant boundaries, and other hard constraints.

But do not confuse a deterministic decision rule with a certain decision signal. “Is this claim supported?” may come from exact citation matching, an entailment model, an embedding threshold, or an LLM judge. Those detectors can be probabilistic, threshold-sensitive, incomplete, or wrong. The policy can deterministically say “fail closed whenever the checker returns unsupported” while the checker remains uncertain about the world.

Your citation example, tightened

If the system has correctly extracted the claims, and the support checker returns supported_claims = 0, then a rule can always route to the fail-closed fallback. That is deterministic conditional on the check result. It is not proof that the response contained no support: citation presence is not citation relevance, and citation relevance is not entailment. Also define what happens on checker timeout or error; fail-closed systems treat that state as “not verified,” not as approval.

A useful interview sentence is: “The enforcement policy is deterministic and fail-closed, but some of its inputs — retrieval, claim extraction, faithfulness scoring, and model-based judging — are probabilistic. Therefore we measure false accepts and false rejects rather than claiming 100% correctness.”

A financial-RAG answer, layer by layer

Imagine a KYC analyst asks whether a document supports a particular review outcome. The system should not jump directly from question to prose. Walk the boundaries:

  1. Govern and scope. Define the allowed use: document assistance and evidence finding, not an invisible autonomous approval. Identify the user role, data sensitivity, retention, and the point where a human must decide.
  2. Ground in authoritative data. Retrieve from versioned policy or case sources, preserve source identity and timestamps, and keep tenant or permission boundaries intact. A model cannot repair an untrusted source.
  3. Constrain the output. Require a schema such as {decision, claims[], citations[], uncertainty}. Reject malformed output instead of guessing how to parse it.
  4. Verify claims. Check every claim against retrieved evidence. Your capstone already separates structural citation integrity from faithfulness; keep both. A citation is a pointer, not proof.
  5. Authorize actions. Allowlist tools, validate arguments, enforce identity and least privilege, and require explicit approval for consequential writes. The model may request approve_case; that does not mean the application may execute it.
  6. Record and escalate. Log the model/version, prompt or policy version, retrieved source ids, tool calls, decisions, failures, overrides, and human disposition. If evidence, schema, authorization, or confidence is insufficient, abstain and route to a person.

Residual risk is still risk. A layered design reduces failure probability and limits blast radius. It does not prove the system is safe. Measure the controls on representative cases, monitor them after deployment, and document what remains outside the system's competence.

Fail closed, not confidently forward

Fail closed means a failed safety check produces no consequential action by default. It may return a useful explanation such as needs_review, but it does not silently continue with an unsupported claim or unauthorized tool call. This is different from “always refuse”: safe systems can proceed when all required checks pass and can explain which boundary caused an abstention when they do not.

The control hierarchy

Use the strongest mechanism available for the property you need:

  • Need valid shape? Use schema validation.
  • Need a source-backed claim? Use citation and claim-level evidence checks.
  • Need to prevent an action? Use authorization and approval outside the model.
  • Need a trace? Use structured audit events.
  • Need safe handling of uncertainty? Use abstention and human escalation.
  • Need less variation? Tune sampling — but never mistake that for any of the controls above.

Temperature and top-p are sampling controls

At each generation step, a language model produces a probability distribution over possible next tokens. Temperature rescales the logits before converting them into probabilities. Lower temperature sharpens the distribution toward the most likely tokens; higher temperature flattens it and permits more variation. It changes how the model samples, not what the application permits.

Top-p, also called nucleus sampling, sorts candidate tokens by probability and keeps the smallest set whose cumulative probability reaches p. Sampling then happens inside that dynamic set. Lower p cuts more of the low-probability tail; top_p=1 does not truncate the distribution. The nucleus-sampling paper shows why decoding strategy alone can change quality even when the underlying model is unchanged. Read Holtzman et al.

For a compliance-oriented answer, you might choose conservative sampling to reduce unnecessary variation. That is an operational choice to evaluate, not a safety guarantee. A low-temperature false claim is still false; a high-temperature answer is not automatically unsafe. Claims, permissions, schemas, and escalation must be enforced by application controls.

Build the control plane

exercises/lesson0010/guardrail_plane.py uses two fictional answer candidates and a tiny policy context. Its claim check is deliberately exact-match and pedagogical, not a replacement for the NLI and evaluation work from lessons 5 and 7. The point is to see independent checks compose into a fail-closed decision.

  1. Run uv sync, then uv run guardrail_plane.py from exercises/lesson0010/. The clean candidate passes schema and claim checks but waits for approval before routing the case to a human.
  2. Run uv run guardrail_plane.py --approve. The candidate now passes all three controls. Approval changed the host policy; it did not change the proposed model output.
  3. Run uv run guardrail_plane.py --scenario risky --approve. Even with approval enabled, the candidate abstains because one claim is unsupported and approve_ticket is not an allowed tool. This is defense in depth.
  4. Read the sampling table. Change --temperature 1.2 and --top-p 0.60. The probability shape and retained token set change, but no tool becomes authorized and no claim becomes supported.
  5. Say the answer aloud. “I use a control plane containing versioned policy, layered guardrails, measurements, audit, and escalation around the data plane. Measurements drive routing per request and policy, threshold, rollout, or rollback decisions across releases. Temperature and top-p control output variability; they are not safety enforcement.”
