Lesson 13 · Interview-first · Hands-on AWS

Your first cloud hop

Make one real Bedrock call, keep the application checks visible, and learn which parts of the system AWS is actually managing.

~45 minutes  ·  Python  ·  lesson 12  ·  roadmap  ·  glossary

Why this lesson

A good answer about an AWS gap is useful, but it does not close the gap. This lesson gives you a small, honest piece of hands-on experience: a Python application sends selected evidence to Amazon Bedrock through the Converse API, receives a response, records usage and latency, and applies a local fail-closed citation check. It is a cloud call, not a claim of production operation.

Keep the first cloud build narrow

Do not start by creating an agent, a vector store, a knowledge base, a VPC, and a dashboard. That is a lot of AWS vocabulary before you have felt the important boundary. Start with one operation:

Your appselect evidence → Bedrock RuntimeConverse API → Foundation modelgenerate text → Your appcheck and route

The exercise keeps retrieval local on purpose. That isolates the new thing, the provider boundary. You already know how to retrieve evidence and check citations. Now you can see exactly what changes when the generator moves from a local stand-in to a managed cloud API.

The AWS concepts that matter here

  • Region: the AWS location used for the API endpoint and model request. Region choice affects availability, latency, data-residency discussion, and sometimes the model ID you can use.
  • Model ID: the identifier sent to Bedrock. It is configuration, not business logic. A model ID can name a foundation model or, where supported, an inference profile.
  • Identity and IAM: the AWS credential chain identifies the caller; an IAM policy decides whether that caller may invoke the selected model. The application should not carry long-lived keys in source code.
  • Runtime API: bedrock-runtime.Converse receives messages and returns a normalized response. The response includes a stop reason, token usage, and latency metrics. Read the Converse documentation.

That list is enough for this build. You do not need to memorize every AWS service name. You need to know which setting changes behavior, where permission is enforced, and which values you can measure.

What crosses the boundary?

local application
  question + selected evidence
        │
        ├── credentials and region select the AWS caller and endpoint
        │
        ▼
Amazon Bedrock Runtime: Converse(model_id, messages, inference_config)
        │
        ▼

The exercise sends the question and two short local passages. Bedrock's Converse documentation says that text, images, and documents supplied as content are not stored by Bedrock for this operation. That statement does not remove your responsibility to review model terms, region routing, logging, application logs, and your own data-handling policy. See the request and response contract.

Notice what does not cross the boundary. The local retriever does not become an AWS Knowledge Base by magic. The local citation check does not become a Bedrock Guardrail. You can add either later, but name the change when you make it.

IAM is a control, not setup paperwork

The application needs permission to invoke the chosen model. A learning role should have the smallest useful permission, not an administrator policy copied from a tutorial:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "InvokeChosenModel",
    "Effect": "Allow",
    "Action": ["bedrock:InvokeModel"],
    "Resource": "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0"
  }]
}

Treat that as a starting shape, not a paste-and-forget answer. Replace the region and model with the ones you actually use. If you invoke through an inference profile, IAM may need permissions for the profile and the underlying foundation models. AWS's policy examples explain the resource forms and recommend reducing broad permissions to the specific use case. Read the Bedrock IAM examples.

For this lab, use your normal AWS profile, SSO session, or assumed role. Do not put access keys in the repository. Check model availability and any first-use requirements in the selected Region before making the call. Read the current model-access guidance.

Guardrails still have layers

Amazon Bedrock can attach a managed Guardrail to a Converse request. It can evaluate configured content policies on input and generated output. That is useful, but it does not replace every control in your application. It does not prove that a cited passage supports a claim, and it does not decide whether a tool action is authorized.

IAM permission        → may this caller invoke this model?
Bedrock Guardrail     → does configured content policy intervene?
Local citation check  → does the answer cite selected evidence?
Application route     → accept, abstain, retry, or escalate?

The exercise accepts a response only when it contains citations from the evidence it received, or an explicit abstention. That is a structural check, not a faithfulness proof. The application still needs the claim-level NLI check from lesson 7 if you want to test whether the cited text entails the claim. To attach a Bedrock Guardrail, pass its versioned ID in the request. AWS documents the guardrailConfig field and the guardrail_intervened stop reason. Read the Converse Guardrail guide.

Build it

exercises/lesson0013/bedrock_grounded.py uses the port and adapter boundary from lesson 12. Its local adapter lets you run the whole route offline. Its Bedrock adapter creates a boto3 runtime client only when you explicitly choose the cloud provider. It also records the usage and latency returned by Converse, rather than treating the answer as the only output that matters.

  1. Run uv sync from exercises/lesson0013/.
  2. Run uv run bedrock_grounded.py. This is offline. Read the evidence IDs, the accepted route, and the fact that usage and latency are None for the local stand-in.
  3. Run uv run bedrock_grounded.py --provider bedrock --dry-run. This creates no AWS client and makes no network call. Inspect the region, model ID, operation, selected evidence, and guardrail setting.
  4. In a personal AWS account or sandbox, confirm your credential source, region, model availability, and least-privilege invoke permission. Check current pricing before invoking anything. Read the official pricing page.
  5. Make one real call with AWS_PROFILE=your-profile AWS_REGION=us-east-1 uv run bedrock_grounded.py --provider bedrock. If your model or region differs, set BEDROCK_MODEL_ID or pass --model-id. Never paste credentials into the command history if your shell records it.
  6. Read STOP REASON, USAGE, LATENCY MS, and ROUTE. The answer is only one part of the observation.

What counts as success

You can point to one real cloud request and explain its boundary: your app selected evidence, IAM allowed a caller to invoke a model in a Region, Bedrock generated a response, and your application still decided whether the response was safe to return. That is a concrete first step. It is more useful than saying “I know Bedrock” after reading a console page.

Turn the call into interview evidence

After you run it, your answer can become specific without becoming inflated:

“I built a small personal Python integration with Bedrock's Converse API.
The retriever and citation gate stayed in application code, while a provider
adapter translated the request to Bedrock. I configured the Region, model ID,
and invoke permission, then inspected stop reason, token usage, latency, and
the fail-closed route. It was a personal learning project, not production
operation. The next question I would investigate is whether a managed
Knowledge Base or a self-managed retrieval layer better fits the data and
provenance requirements.”

That answer has an experience boundary, a concrete build, and a limit. It also gives the interviewer somewhere useful to probe.

Stuck? Ask your teacher

Ask about IAM resource ARNs, model access errors, inference profiles, the difference between Bedrock Runtime and a Knowledge Base, or what the response usage and latency fields mean. We can debug the actual output instead of guessing.

Predict then compare · boundary

A response contains a valid-looking citation, but the citation does not support its claim. Which control should reject it? State what the other three layers do instead.

Compare your answer

The application’s claim-level faithfulness check should reject it. IAM decides whether a caller may invoke the model. A Bedrock Guardrail applies configured content policy. A citation-shape check only verifies that a known evidence ID appears. None of those alone proves entailment.
