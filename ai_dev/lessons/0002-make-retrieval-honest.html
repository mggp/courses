Make retrieval honest

Chunking real documents, then measuring whether retrieval actually found the right chunks. This is the step between "a demo" and "a system you'd ship."

Why this lesson

A compliance officer won't accept "the model said so" — they need the answer traced to a policy document. A language learner needs to click through to the lesson their answer came from. Both demands rest on the same thing: retrieval must actually find the right chunk. Last lesson you built retrieval; this lesson you find out whether it works.

Retrieval's unit is the chunk

Retrieval ranks chunks — the pieces you embed and hand to the generator. Simon Willison's RAG setup is a working example of the principle: he extracted every paragraph of his blog, embedded each paragraph, and answered questions by retrieving paragraphs. The whole point of chunking is that the answer to a question fits inside one retrievable unit: "Embedding paragraphs from my blog with E5-large-v2".

Two ways to make chunks

Structure-based — split on the document's own boundaries: paragraphs, sections, list items. Meaning stays intact, but length varies, and a question whose answer spans two paragraphs needs both to be retrieved.

Fixed-size windows — slide a window of N characters (or tokens) across the text, with overlap so a fact straddling a boundary isn't cut in half. Uniform length, guaranteed coverage — but a window is a blunt instrument: it can glue several unrelated facts together, diluting the context you feed the model.

The hard ceiling. Your embedding model truncates text at a fixed length — the harness prints it: 256 tokens for all-MiniLM-L6-v2 (≈1000 characters, per its model card). Anything past that is silently dropped, so chunks must stay under it or you're embedding a truncated shadow of the chunk.

Every chunk carries its name

Give each chunk an id (and eventually a source — which file, which lesson). Retrieval then returns where the answer lives, which is exactly what a citation needs. No id, no provenance, no compliance answer.

Measuring retrieval: recall@k

To score retrieval you need a gold answer: a question paired with the sentence that must end up in the retrieved context. Then the metric is:

recall@k = (gold chunks found in top-k) / (gold chunks)

Measure at the k you will actually feed the generator — retrieving 100 chunks to get a perfect score is cheating yourself.

This is a real field. The "move from vibe checks to evaluation loops" is the entire pitch of Ragas, the standard open-source framework for evaluating RAG. What you're about to build by hand is the same idea with zero dependencies.

Build it

In exercises/lesson0002/ you'll find a tiny corpus — corpus.md, a product brief for Lingua, the language-learning app from your mission — and the harness evaluate.py. The two chunkers and the scoring are small enough to know cold:

def chunk_by_paragraph(text):
    paras = [p.strip() for p in re.split(r"\n\s*\n", text) if p.strip()]
    return [(f"p{i}", p) for i, p in enumerate(paras)]

def chunk_fixed_size(text, size=600, overlap=120):
    text = re.sub(r"\s+", " ", text).strip()
    chunks, start = [], 0
    while start < len(text):
        end = min(start + size, len(text))
        chunks.append((f"f{len(chunks)}", text[start:end]))
        if end == len(text):
            break
        start += size - overlap
    return chunks

  1. In exercises/lesson0002/, run uv sync then uv run evaluate.py. You should see paragraph chunking score 0.75 and one row flagged <-- miss.
  2. Find the miss. For "What does the tutor do when it cannot find an answer?", the top-3 are p3, p4, p9 — all about the tutor and retrieval. The gold chunk p10 ("…says it does not know rather than guessing") never surfaces. Read it and the query again: the words of the answer don't appear in the query. Semantic search is not synonym-aware magic — no vocabulary overlap, no hit.
  3. Spot the fake 1.00. Fixed-size 600/120 shows recall 1.00. Look at its chunk count: three. With 3 chunks and k=3, the top-3 always contains everything — the score is vacuous. This is why the measurement only bites when the index is much larger than k. On a real corpus of thousands of chunks, k=3 is a real constraint.
  4. Shrink the windows. Run uv run evaluate.py 300 50 then uv run evaluate.py 150 30. Chunk counts rise (5, then 9) and recall falls back to 0.75 — and the same question misses. Chunk size didn't cause this failure, so chunk size can't fix it.
  5. Name what you now control. You can measure any chunker, any k, any corpus. When you swap corpus.md for a real document — a policy text, a grammar reference for Lingua — you'll know in one number whether retrieval is ready for the generator.
  6. (Optional) Feed the winning chunks with their ids into the generate() prompt from lesson 1, so the answer cites p10 by name. That is a citable answer.
