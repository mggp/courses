Two eyes: hybrid retrieval

One retrieval system has one blindness. Run two systems with different blindnesses side by side, fuse their results, and measure whether the sum beats either part.

~50 minutes  ·  Python  ·  lesson 1  ·  lesson 2  ·  glossary

Why this lesson

Strip the fintech problems you named — fraud detection, KYC auditing, loan underwriting, credit risk, document Q&A — down to the mechanical core and they share one engine: find the right record among millions. A suspicious transaction narrative against known fraud patterns. An onboarding file against prior audits. An application against precedent decisions. That is retrieval, and the measurement rules in this lesson hold no matter which store you run — MySQL, DynamoDB, Postgres, or a separate index. (For Lingua, still hypothetical, every point of recall is a learner who gets the right lesson cited instead of a near-miss.) The lesson-2 harness becomes the referee: you will not trust fusion on faith.

Where lesson 2 left you

In lesson 2 you discovered that your embedding model ranks on surface form: for "cannot find an answer" the winners shared literal words ("cannot", "answers") while the true chunk sat at rank 4, and the paraphrase gap survived every chunk size. You also mapped where a fix can live, in three pipeline layers: the chunk layer (how documents are cut — ruled out there), the retrieval layer (how the search step finds chunks), and the query layer (how the question itself is phrased). This lesson builds the first fix in the retrieval layer: a second, differently-blind eye. The query layer belongs to lesson 4.

Two eyes, two blindnesses

Dense search — what you've built. Every chunk becomes a fixed-length vector; you rank by cosine similarity. Sees meaning, misses exact words: the "engine" query from your new gold set ranks the right chunk 8th because the answer's other words don't match.

Keyword search — the classic scorer, BM25, Elasticsearch's default for 25 years. Sees exact words (after analysis), misses meaning: "long-term recall sharp" shares no word with "spaced repetition", so it scores zero.

They are mirror-image systems. Feed a query to both and let each cover the other's blindness — but measure that it actually does.

BM25, from first principles

Before scoring, text passes through analysis: lowercasing and stemming, so "reviewed" and "review" become the same token. Then each query term contributes:

score = IDF * (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * doclen / avg_doclen))

IDF  = log((N - df + 0.5) / (df + 0.5) + 1)   # rare terms matter more
tf   = times the term appears in the doc        # capped by k1=1.5
b    = length normalization (0.75)              # short docs aren't punished

Read the IDF. In your corpus, "authentication" appears in one document out of 24 → matching it is almost proof of relevance. "the" appears everywhere → IDF ≈ 0. This is why keyword search is brilliant at jargon and hopeless at paraphrase. BM25 is the 1990s probabilistic relevance framework and still the default wherever text search ships — Elasticsearch, Postgres full-text search, MySQL FULLTEXT indexes. Where the index lives is a stack decision; the scoring is the same.

Why you can't just average the scores

BM25 scores (roughly 0–10) and cosine similarities (0–1) live on different scales and distributions — averaging silently lets one system dominate. RRF (reciprocal rank fusion) throws scores away and votes by rank:

def rrf(lists, k=60):
    out = {}
    for ranked in lists:               # one list per system
        for rank, doc_id in enumerate(ranked, start=1):
            out[doc_id] = out.get(doc_id, 0.0) + 1.0 / (k + rank)
    return out

Think of an election: each system is a voter, and a chunk that places high on either ballot accumulates points. The 60 softens the gap between adjacent ranks — you'll tune it.

What does the 60 actually do? RRF's k is a rank-damping constant — RRF never sees scores, so k is not in any score's units (it is not "close to the BM25 scale" or anything else; it's scale-free). It sets how steeply reward falls off within one list: rank 1 vs rank 10 drops 90% at k=0, 45% at k=10, 13% at k=60, under 1% at k=1000. Small k: each system's top pick dominates the fusion. Large k: position barely matters and the score approaches "how many lists you appear in." k=60 is the robust default from the original RRF paper (Cormack et al., 2009) — standard, not sacred.

Where this lives in your stack. On Postgres you'd use pgvector for the dense half; on MySQL or DynamoDB you'd typically keep vectors in a dedicated index or a managed search/vector service and join by record key. The fusion math is exactly what those services call "hybrid search" under the hood — you're learning the recipe before renting the appliance.

Build it

In exercises/lesson0003/ the corpus is a fuller product brief for Lingua — still hypothetical, every specific illustrative — at 24 paragraphs, and hybrid.py extends lesson 2's harness with BM25 and RRF. The gold set deliberately contains each failure class:

GOLD = [
    ("How does the tutor avoid teaching wrong facts?",  "The tutor answers only from the course material..."),
    ("When will a word be reviewed next?",              "The scheduler computes the next review date"),
    ("What does the tutor do when it cannot find an answer?", "the tutor says it does not know rather than guessing"),
    ("Which engine suggests the next lesson?",          "suggests new lessons based on recently missed words"),
    ("What method keeps long-term recall sharp?",       "Spaced repetition schedules the review of each word..."),
    # ...
]
  1. Run uv sync then uv run hybrid.py. You should see the three columns disagree and the story in the averages: dense 0.67, bm25 0.67, fused 0.83.
  2. Read the disagreement rows. "Which engine suggests the next lesson?": dense missed it (the right chunk ranked 8th), bm25 nailed it (rank 1), and fused recovered it. "What method keeps long-term recall sharp?": the mirror — bm25 scored zero, dense nailed it, fused kept it. And "cannot find an answer": all three miss — the paraphrase wall stands.
  3. Work the fusion by hand. For the engine query, p22 is 6th in dense and 1st in bm25: 1/(60+6) + 1/(60+1) = 0.0315. Its rival p2 is 3rd in dense and 5th in bm25: 1/(60+3) + 1/(60+5) = 0.0313. p22 wins by two thousandths. That margin is the whole reason you measure.
  4. Turn the knob. Run uv run hybrid.py 3 10 — with RRF k=10 the recovery margin grows (p22 gets 1/11 ≈ 0.09). Now run uv run hybrid.py 5 60 — even the paraphrase row is found and fused hits 1.00. Why? k=5 on a 24-chunk index is 20% of the corpus: BM25's weak "tutor" match finally enters the context. That is not recall, it is a toy-corpus artifact — the lesson-2 scale caveat again.
  5. Make fusion lose. Leave the gold set and explore one query of your own: uv run hybrid.py --query "What stops old vocabulary from being forgotten?" --gold "Spaced repetition schedules the review of each word at growing intervals". Nothing was added to the corpus for this — the correct answer is already there: paragraph p5, the very chunk gold question 6 targets. ("Gold-less" only meant this question isn't among your six; you judge the answer by reading p5, and the --gold flag checks it for you.) Rankings are deterministic for a fixed corpus and model, so you should reproduce exactly this: dense ranks p5 second (recall 1.00), bm25 finds only junk — p1 via "vocabulary", p7 via "being" — and the fused top-3 crowds p5 out (recall 0.00). Fusion is a compromise: one voter's noise can bury the other's good hit. That is exactly why you truncate the ballots, weigh the voters, and re-measure. And note the corollary: if you add or change corpus text, these rankings will shift — which is precisely what the harness exists to catch.
  6. Name what survives. The one row that no knob fixes is the paraphrase row — neither system shares any word or meaning with "says it does not know rather than guessing." That failure lives in the query, not the index, and it is the next lesson's target.
