Why this lesson

You already have genuine material to discuss: maintaining FastAPI services, Django experience, a personal LangGraph tool, MCP integration, and local RAG work. The interview risk is not lacking vocabulary; it is giving a framework or cloud answer that sounds more hands-on than it is. This lesson turns the vocabulary into a truthful delivery story.

FastAPI versus Flask is a boundary decision

Do not answer this as “FastAPI is modern and Flask is old.” Ask what the application needs and what the team already operates.

  • FastAPI: a type-hint-driven API framework with Pydantic-backed validation, OpenAPI-based documentation, and built-in dependency injection. It is a natural fit when typed HTTP contracts, generated API documentation, and concurrent I/O are central concerns. The framework's own documentation describes its Starlette and Pydantic foundations and its async/await support. Read the feature list.
  • Flask: a small, explicit WSGI-oriented framework with a broad extension ecosystem. Flask can define async views, but its documentation explains that each request still occupies a worker under WSGI; async is useful for concurrent I/O inside that request, not a universal speed or concurrency guarantee. Read the async caveat.

A defensible comparison is: “FastAPI gives me typed request/response contracts, automatic OpenAPI documentation, validation, and dependency injection with an async-friendly API boundary. Flask gives me a smaller, explicit core and a mature extension ecosystem. I would choose based on the existing codebase, contract and validation needs, I/O pattern, deployment model, team familiarity, and measured operational behavior—not on a blanket performance claim.”

For your own experience, say: “I have maintained FastAPI services, so I can discuss that from practice. My Flask comparison is architectural unless I have a specific Flask system to describe.” That sentence is more credible than inventing a Flask migration story.

ASGI and WSGI are interface protocols

The important distinction is not “old sync framework versus new async framework.” WSGI and ASGI define how a server calls an application. The server still owns sockets and HTTP parsing. The interface determines what the application can receive, return, and await.

# WSGI: one synchronous callable for an HTTP request
def application(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"hello"]

# ASGI 3: one async callable for a connection
async def application(scope, receive, send):
    await send({"type": "http.response.start", "status": 200, "headers": []})
    await send({"type": "http.response.body", "body": b"hello"})

WSGI gives the application a CGI-like environ dictionary and a start_response callback. The application returns an iterable of byte strings. That is a good simple contract for ordinary HTTP request and response work. It does not provide an async event protocol or a portable WebSocket model. The contract is specified by PEP 3333.

ASGI gives the application a scope, an awaitable receive function, and an awaitable send function. HTTP request bodies, response chunks, WebSocket messages, and lifecycle events travel as messages. An HTTP scope usually lasts for one request. A WebSocket scope can last for the whole connection. The contract is defined by the ASGI specification.

  • Concurrency: a WSGI deployment usually gets concurrency from multiple processes or threads. An ASGI deployment can interleave many tasks on an event loop when the application awaits non-blocking I/O. ASGI can also use multiple worker processes.
  • Blocking work: async def does not make a blocking database driver or model SDK non-blocking. In an ASGI worker, blocking code can stall other tasks. Use an async client or explicitly offload blocking work to a thread or process.
  • Protocols: WSGI is centered on HTTP request and response. ASGI models HTTP, WebSockets, and lifespan events through the same general message pattern.
  • Streaming: WSGI can return an iterable for HTTP streaming. ASGI makes incremental send events and long-lived connections first-class, which is a better fit for token streaming and WebSockets.
  • Compatibility: an ASGI server can run a WSGI application through an adapter, but the adapter cannot invent WebSocket or non-blocking behavior that the WSGI application does not expose.

Interview answer: “WSGI is a synchronous two-argument application interface built around an environment dictionary, a response callback, and a returned iterable. ASGI is an async message interface with scope, receive, and send, so it can represent HTTP, WebSockets, streaming, and lifespan events. ASGI can improve I/O concurrency when the whole path is non-blocking, but it does not make CPU-heavy or blocking code fast. For an AI API I would check whether the model, database, and HTTP clients are async-capable, then measure latency and worker behavior.”

Use SOLID as a diagnosis, not a recital

SOLID is useful when it explains a seam in the design. For an AI API, keep the HTTP adapter, application use case, model provider, retrieval system, policy checks, and audit sink separate:

HTTP routeparse transport → Use caseorchestrate work → Portsmodel + retrieval → AdaptersSDKs + stores
  • Single Responsibility: the route handles HTTP, the use case coordinates, the provider adapter speaks an SDK, and the audit sink records events. None should own all four jobs.
  • Open/Closed: add a new model-provider adapter without editing the core use case.
  • Liskov Substitution: every adapter must honor the same port contract: valid inputs, a predictable result, and defined failure behavior.
  • Interface Segregation: depend on small, cohesive ports such as ModelPort, RetrieverPort, and AuditPort, not one giant “AI service” interface.
  • Dependency Inversion: the high-level use case depends on those abstractions; provider SDKs are injected at the edge.

A port is an application-owned interface for one role that can change independently. In this exercise, ModelPort.generate() says what the use case needs from a model. AuditPort.record() says what it needs from an audit sink. Neither interface mentions boto3, an HTTP client, a database table, or a provider's native request shape.

# Too broad for a use case that only generates and audits
class AiPlatform(Protocol):
    def generate(self, request): ...
    def embed(self, text): ...
    def retrieve(self, query): ...
    def invoke_tool(self, name, arguments): ...
    def record_audit(self, event): ...

# Role-specific ports
class ModelPort(Protocol):
    def generate(self, request): ...

class AuditPort(Protocol):
    def record(self, event): ...

The word small refers to the client's view, not to an arbitrary one-method rule. A port should contain the operations one consumer role needs and no provider-specific extras. If a service depends on a giant interface, every implementation and test must understand methods that service never uses. That is the Interface Segregation Principle in concrete terms.

Your deep-module analogy is useful, but it names a different property. Interface Segregation asks which operations should this client depend on? A deep module asks how much useful work does a simple public interface hide? A ModelPort can be a small port and a deep module if its adapter hides retries, serialization, authentication, and provider errors. A one-method wrapper that merely forwards a call is small but shallow. Keep the two ideas related, not interchangeable.

class ModelPort(Protocol):
    def generate(self, request: GenerationRequest) -> GenerationResponse: ...

class AnswerService:
    def __init__(self, model: ModelPort, audit: AuditPort): ...

This is not architecture for its own sake. The seam lets you test the use case with a fake provider, compare providers without rewriting business logic, and keep cloud-specific retries, authentication, telemetry, and request translation at the adapter boundary. Stop adding abstractions when the seam has no independent reason to change.

Foundation models and RBAC

A foundation model is usually broadly pre-trained on diverse data at scale and intended to support many downstream tasks. Pre-training is part of the story, but “pre-trained” alone is not the definition. A task-specific image classifier may be pre-trained and still not be a foundation model. A foundation model may later receive instruction tuning, alignment, fine-tuning, or other adaptation. AWS uses the term for models exposed through Bedrock that can support tasks such as text generation, image generation, or embeddings. Read AWS's model overview.

RBAC means role-based access control. It grants permissions through roles rather than assigning every permission directly to every person. The useful mental model is principal + role definition + scope: a user, group, service principal, or managed identity receives a role such as reader or contributor at a subscription, resource group, or resource scope. RBAC is authorization, not authentication. Azure's documentation describes this model and its role-assignment structure. Read the RBAC overview.

  • Amazon Bedrock: a managed service for access to foundation models. Its Knowledge Bases capability is a managed RAG surface; evaluate how it fits your ingestion, retrieval, provenance, IAM, and control-plane requirements. Read the overview.
  • Microsoft Foundry: the current Microsoft platform brings models, agents, tools, observability, governance, identity, RBAC, and networking into a managed surface. Distinguish a prompt agent or hosted agent you learn from documentation from one you have operated. Read the current overview.
  • Vertex AI: describe it as a managed Google AI-platform surface you would investigate through its current model, deployment, evaluation, identity, networking, and monitoring documentation. Do not turn a quickstart read into production experience.

The evaluation questions remain portable: What is managed? Where does data go? How are identities and permissions enforced? How do I bring my own retrieval and guardrails? What are the latency, cost, quota, observability, and rollback characteristics? Which parts remain application code?

Build the delivery story

exercises/lesson0012/delivery_story.py is an offline design seam. Its AnswerService depends on ModelPort and AuditPort, while a local adapter stands in for a provider SDK. The provider labels are deliberately not cloud integrations; they let you practise the architecture and the honest gap statement without making a network call or a false experience claim.

  1. Run uv sync, then uv run delivery_story.py from exercises/lesson0012/. Read the dependency boundary and the SOLID checks.
  2. Run uv run delivery_story.py --framework fastapi --provider bedrock. The output gives an architectural comparison and an explicit “not hands-on” boundary.
  3. Run uv run delivery_story.py --framework flask --provider foundry. Notice that changing the framework or provider label does not require changing AnswerService.
  4. Read the adapter and port definitions. Identify which line would change if a real provider SDK were introduced, and which line should remain unchanged.
  5. Say the answer aloud. “I can speak from practice about maintaining FastAPI services and integrating MCP tooling. I have not operated Bedrock, Foundry, or Vertex in production. I would isolate provider SDKs behind ports, then evaluate identity, network, retrieval, guardrails, evaluation, latency, cost, and monitoring before choosing a managed surface.”
