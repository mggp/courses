Similarity is not a relationship

Choose the retrieval operation that matches the question, then measure whether your chunk boundaries preserve the evidence.

~35 minutes  ·  Python  ·  lesson 10  ·  roadmap  ·  glossary

Why this lesson

Your diagnostic already had the important vector-versus-graph intuition. This lesson makes it interview-ready: vector similarity finds semantically related evidence, graph traversal follows explicit relationships, and a hybrid system can use both. The second win is to explain fixed-size versus semantic chunking without claiming that “semantic” automatically means better.

Choose the retrieval operation, not the product

A vector index represents text or entities as points in an embedding space and retrieves nearby points. It is a strong fit when the question is about meaning in unstructured text: “What does the policy say about exposure limits?” Similar wording is not required; semantic similarity is the signal.

A graph database represents entities as nodes and facts about their connections as typed edges with properties. A traversal follows those edges and applies explicit constraints. It is a strong fit when the question is about paths, ownership, dependencies, or multi-hop relationships: “Which subsidiaries are ultimately controlled by this beneficial owner?”

Use a hybrid when the question has two jobs

Many useful questions need both structure and text. Use the graph to find the relevant entities or path, then use vector retrieval to find the filing or paragraph that explains and supports it. Or retrieve text first, extract entities, and traverse the resulting subgraph. The boundary is architectural; it is not tied to a particular vendor.

  • Vector: semantic evidence, paraphrases, policies, explanations, and unstructured passages.
  • Graph: explicit entities, typed relationships, multi-hop paths, filters, and consistency constraints.
  • Hybrid: relationship-constrained evidence, such as “which controlled companies are mentioned in the filing, and what passage supports the link?”

Do not confuse two meanings of hybrid

Earlier lessons used hybrid search for keyword plus dense retrieval. Here, vector-graph hybrid means semantic retrieval plus graph traversal. Both are valid combinations, but they solve different blind spots and should be named precisely.

Beneficial ownership, end to end

Suppose the question is: “Which companies are ultimately controlled by Elena Ruiz, and which filing supports each relationship?” The system does not ask one database to magically answer everything. It turns source records into two connected representations:

Elena Ruiz ──BENEFICIAL_OWNER_OF──> Northstar Holdings
Northstar Holdings ──OWNS 80%──> Meridian Finance
Meridian Finance ──OWNS_VOTING_SHARES──> Harbor Credit
  1. Ingest and extract: parse filings and registry records into entities and typed edges. Every edge keeps provenance, for example p1, p2, or p3 for the source passage that created it.
  2. Traverse the graph: start at Elena Ruiz and follow allowed ownership edges. The result is a path to Meridian Finance and then Harbor Credit. This is why graph traversal is useful: it exposes the explicit chain instead of hoping three separate paragraphs happen to rank together.
  3. Retrieve the evidence: use the edge provenance to fetch the exact passages, or use vector retrieval over the filings to find the relevant prose. The vector step supplies readable evidence and citations; it does not decide whether the ownership path exists.
  4. Apply the domain rule: only call the result “ultimate control” if the business/legal policy says this edge combination qualifies. Otherwise report the narrower fact: “an ownership path was found.” Beneficial ownership, legal control, and economic ownership are not interchangeable labels.

What the hybrid answer might contain

“The graph finds the path Elena Ruiz → Northstar Holdings → Meridian Finance → Harbor Credit. Passage p1 supports Elena's beneficial ownership of Northstar; p2 supports Northstar's 80% ownership of Meridian; p3 supports Meridian's voting-share relationship with Harbor. Under the stated control rule, Harbor qualifies; without that rule, the system should claim only that it found this ownership path.”

Interview-safe answer: definition → trade-off → example → limit. “Vector search is good for semantic evidence but does not guarantee an explicit relationship. Graph traversal makes relationships and constraints queryable but requires entity and edge modeling. For a beneficial-ownership question, I would use graph traversal to establish the path and vector retrieval to fetch the source passages, then evaluate recall, precision, faithfulness, latency, and maintenance cost.”

Chunking changes what retrieval can see

Chunking is not merely a preprocessing detail. It defines the units that can be retrieved, cited, reranked, and passed to the generator. The same embedding model can behave differently when the boundaries change.

  • Fixed-size chunking cuts by a token or word budget, usually with overlap. It is predictable, inexpensive, easy to reproduce, and a useful baseline. Its weakness is that a boundary can split a definition, table, or argument.
  • Semantic chunking tries to place boundaries where topic or sentence meaning changes. It can preserve more coherent units and variable-length context, but it costs more, depends on thresholds or a model, and still needs a maximum size. “Semantic” is a hypothesis about useful boundaries, not a quality guarantee.
  • Structure-aware or hierarchical chunking uses headings, sections, parent/child relationships, or document layout. It can retrieve a precise child while returning a broader parent for context, at the cost of more indexing and assembly logic.

Overlap can preserve continuity across a fixed boundary, but it duplicates content and can increase index size and context noise. A larger chunk may preserve context while lowering retrieval precision; a smaller chunk may improve precision while losing the surrounding qualifier. The correct setting is corpus- and query-dependent.

Measure the chunker, do not admire it

To compare chunking strategies, hold the corpus, embedding model, retriever, top-k, and generator constant. Change only the chunker. Then use a held-out query set with known relevant evidence and compare:

  • Recall@k: did the needed evidence enter the retrieved set?
  • Precision@k: how much of the retrieved set was relevant rather than noise?
  • Faithfulness and attribution: did the answer use the retrieved evidence correctly and cite the supporting unit?
  • Operational cost: ingestion time, index size, retrieval latency, context tokens, and maintenance complexity.

A chunker can improve recall while hurting faithfulness by returning too much loosely related context. It can improve precision while hurting recall by splitting the only complete answer across separate chunks. This is why chunking belongs in the evaluation loop from lesson 7, not in a list of universal magic numbers.

Build the retrieval decision card

exercises/lesson0011/retrieval_architecture.py is an offline inspection tool. It recommends vector, graph, or hybrid retrieval from the shape of a question, then prints the boundaries produced by a fixed-size baseline and a deliberately transparent semantic proxy. The proxy uses lexical overlap; it is not an embedding model or a production chunker.

  1. Run uv sync, then uv run retrieval_architecture.py from exercises/lesson0011/. The default question asks for ownership relationships and supporting filing evidence, so the recommendation should be HYBRID.
  2. Run uv run retrieval_architecture.py --show-chunks. Compare where fixed-size chunks cut the document with where the semantic proxy changes topic.
  3. Try uv run retrieval_architecture.py --query "What controls limit aggregate exposure?" --show-chunks. This is primarily a vector evidence question.
  4. Try uv run retrieval_architecture.py --query "Which entities are ultimately owned by Elena Ruiz?". This is primarily a graph traversal question.
  5. Change --fixed-size, --overlap, --semantic-max, and --threshold. Treat the printed boundaries as hypotheses; your evaluation set decides whether they help.
  6. Say the answer aloud. “I choose vector retrieval for semantic evidence, graph traversal for explicit multi-hop relationships, and a hybrid when I need both a relationship-constrained set and source passages. For chunking I start with a reproducible baseline, then compare semantic or hierarchical boundaries using held-out retrieval, faithfulness, latency, and cost metrics.”
