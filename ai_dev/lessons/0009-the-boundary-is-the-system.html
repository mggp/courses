Lesson 9 · Interview-first · Agent systems

The boundary is the system

An LLM becomes an agent only when a controlled loop connects decisions to tools, observations, and stopping rules.

~35 minutes  ·  Python  ·  lesson 8  ·  roadmap  ·  glossary

Why this lesson

Your interview diagnostic already had the core idea: an LLM is a component; the surrounding loop decides whether to call a tool, how to use its result, and when to stop. This lesson makes the integration boundaries precise enough to explain your real LangGraph and MCP work without turning either into a framework buzzword. The tangible win is a clean answer to: what is an agent, what does MCP do, and why is this not automatically a multi-agent system?

Start with the smallest honest definition

A workflow is an LLM-and-tool system whose path is mostly fixed in code: call A, validate it, call B. An agent is a system in which the model dynamically selects the next step or tool based on the task and the observations it receives. Anthropic uses this same distinction and recommends adding complexity only when it improves a measured outcome. Read the source before reaching for a framework.

LLMproposes a next step → Tooldoes external work → Observationreturns ground truth ↺ Stop / continuebounded by policy

The model does not magically execute Python, query a database, or know whether an action succeeded. The host application turns a model decision into a validated call, executes it, records the result, and presents that observation to the next turn. The loop needs a maximum-step bound, error handling, and a human checkpoint for consequential actions. The ReAct paper is the research anchor for interleaving model decisions with environment actions and observations; you do not need to expose private chain-of-thought to implement the loop.

Five surfaces, five jobs

These words are easy to blur together. Keep the contracts separate:

  • Tool — a schema-described callable capability. It may read data or change external state. Treat its input, output, permissions, timeout, and side effects as an API contract.
  • Resource — addressable context or data for the user or model to read. A policy document is a resource; “write a note to ticket T-42” is a tool call.
  • Prompt — a message or template that shapes an interaction. It is not a tool and does not grant permission to perform an action.
  • Skill — a reusable package of instructions and supporting material. The Agent Skills specification uses a directory with SKILL.md plus optional scripts, references, and assets. A skill tells an agent how to do a class of work; it is not itself a callable operation. Read the specification.
  • MCP — a protocol boundary for connecting an LLM application to external data and capabilities. Its current specification describes a host (the LLM application), client (a connector inside the host), and server (the service providing capabilities), with server features for resources, prompts, and tools. It standardizes integration messages and discovery; it does not choose your planning algorithm, persist your agent memory, or define your application's authorization policy. Read the MCP specification.

Interview-safe phrasing. Say “MCP standardizes how an application discovers and uses external tools, resources, and prompts.” Do not say “MCP is the agent,” “MCP provides planning,” or “MCP makes a tool safe.” Safety still belongs to the host, server, identity layer, and approval policy.

MCP is a boundary, not the brain

Think of MCP as an integration contract, similar in spirit to how a protocol lets many clients connect to many services without each pair inventing a custom interface. The host still owns the user experience and the trust decision. The model may propose a tool call; the host validates it and decides whether to run it. The server still owns the implementation and its access to data.

HostLLM app + policy → MCP clientconnection inside host ⇄ MCP servertools + resources + prompts → External systemdatabase / API / files

The MCP tools specification describes tools as model-controlled capabilities, but it also recommends that a human can deny invocations and that the interface makes tool use visible. It further warns that tool descriptions and annotations are untrusted unless they come from a trusted server. That is an important boundary lesson: a protocol can carry a capability description; it cannot turn an untrusted capability into a trusted one. Read the tools specification.

Build it without an LLM first

exercises/lesson0009/agent_boundaries.py is intentionally offline. Its deterministic model_decide function stands in for an LLM so you can inspect the control loop before adding model latency, token cost, or nondeterminism. The catalog is “MCP-style,” not a full MCP implementation: it makes the boundary visible without hiding the lesson inside a client library.

  1. Run uv sync, then uv run agent_boundaries.py from exercises/lesson0009/. Identify the four different surfaces printed before the trace: tools, a resource, a prompt, and a skill.
  2. Read the trace. The sequence is model decision → tool call → tool result → next model decision. The first tool reads a ticket. The second would write a note. The result is an observation, not a new instruction: the loop decides what to do with it.
  3. Notice the refusal. The default run refuses add_note because it can change external state. The prompt requested the action, but the prompt did not authorize it. The runtime policy did.
  4. Run uv run agent_boundaries.py --approve. The model decision is unchanged; only the host's approval policy changes. This is the difference between “the model asked” and “the system allowed.”
  5. Map it to your experience. In your test-validation agent, the test runner or validator is the external capability, the test result is the observation, and the stopping rule decides whether the loop is finished. In your maintained FastAPI/MCP work, describe the integration boundary you actually configured; do not claim that MCP supplied planning, memory, or production authorization for you.

Your interview answer

Use the course answer shape: definition → trade-off → one real example → limit or control. Example: “An agent is an LLM-driven control loop that can choose tools from environmental feedback. It is more flexible than a fixed workflow but costs more and can compound errors. I built a personal LangGraph tool that validates tests generated by a coding agent; the test result is feedback to the loop. I would bound iterations, validate tool inputs, log calls, and require approval for side effects.” Adjust the details to exactly what you built.

Do not add agents by multiplication

A multi-agent system is multiple agents coordinating, not merely one agent with several tools. Start with one agent. Add multiple agents only when you can name the measurable reason: independent work that can run in parallel, separate context windows, or a division of tools and responsibilities that improves evaluation. Anthropic's multi-agent research system reports the upside of parallel, context-isolated exploration alongside much higher token use and coordination complexity. See the engineering report.

For a KYC audit, parallel independent checks might justify separate workers if the checks truly do not depend on one another. For a simple document question, multiple agents usually add latency and more failure surfaces without improving the answer. The design question is not “can I use multi-agent?” It is “what measured bottleneck does another agent remove?”
