Lesson 14 · Agent architecture · Memory

Memory is a policy, not a pile of transcripts

Separate thread state from cross-thread memory, then define how information is written, selected, and placed in the model input.

~15 minutes  ·  Architecture  ·  agent boundary  ·  glossary

Why this lesson

You already identified the main split correctly. A tool result belongs to the current run or thread, while a programming-language preference should survive into later threads. The next step is to turn that intuition into an implementation design you can build and explain in an interview.

The model has input, not memory

An ordinary model call does not reach into your session database. It can use only the tokens and other supported inputs supplied for that inference. The host application creates the appearance of memory by saving state, selecting some of it later, and placing it back into the model input.

Writesave an event or fact → Selectfind what matters now → Injectbuild model input → Useone inference

This is the key boundary. Stored means the application can recover information. In context means the model can use it on this call. MemGPT makes the distinction explicit: information outside the fixed context window must be moved into the main context before the model can use it. Read the memory hierarchy.

Classify by scope before storage technology

Short-term and long-term describe scope, not whether the bytes live in RAM or on disk.

LangGraph reflects this split directly. A checkpointer saves thread state and can use a database in production. A store shares user or application data across threads. Its documentation also warns that long message histories can exceed the context window, so applications trim, delete, or summarize them before inference. Correction to your starting model

Your ReAct description is right for a small loop whose host resends every message. It is not a general guarantee. A production host may persist the complete event history while sending the model only recent messages, a summary, selected tool results, and retrieved memories. The archive and the current context are different objects.

Archive here means the application's durable event history. It may contain every user and assistant message, tool request, tool result, state transition, timestamp, and approval. It supports resuming, auditing, debugging, replay, and rebuilding summaries. It is not automatically long-term memory, and the model does not automatically read it. A memory policy promotes or retrieves selected information from that history when a later inference needs it.

In a small append-only loop, prior messages and tool events normally remain in the same order and the host adds the newest event at the end. That shape is friendly to prefix caching. OpenAI's API caches repeated prompt prefixes, so an unchanged history can reuse the earlier prefix while the latest suffix is new. Trimming, summarizing, or inserting changing memory near the beginning changes the token sequence and reduces the reusable prefix. See the current prompt-caching guide.

Once the history becomes too large, the host may replace an older span with a summary or omit it from model input while retaining the original events in the archive. Removed events are not usually reinserted one by one on every turn. The host retrieves an old event only when it becomes relevant again. Keep a tool request and its result together while a later step still depends on them, then summarize or omit completed detail according to policy.

Design the read and write policy

A database alone gives you persistence, not useful memory. For every candidate memory, answer these questions:

  1. Scope. Is it useful only inside this thread, or across future threads? Which user, tenant, or agent owns it?
  2. Write. What qualifies for storage? Use explicit user requests or application rules for stable facts. Do not promote every model claim into truth.
  3. Select. Is the item always needed, fetched by an exact key, or searched by meaning? Set a small result limit.
  4. Inject. Where will it enter the model input, and how much token budget may it consume? Label its source and age.
  5. Maintain. How can a user correct, delete, or supersede it? What happens when two memories conflict?

The CoALA paper gives this host-level design a useful vocabulary. Reasoning updates working memory, retrieval reads long-term memory, and learning writes long-term memory. The LLM is one component inside that larger architecture. Read section 4.1 and the surrounding action model.

Apply it to an AI tutor

# Thread state, checkpointed under thread_id
current_exercise = "Translate: I missed the train"
latest_tool_result = {"grammar_check": "past tense is correct"}
attempts_this_thread = 2

# Cross-thread memory, stored under (tenant_id, user_id, "profile")
preferred_programming_language = {
    "value": "Python",
    "source": "user-stated",
    "recorded_at": "2026-09-02"
}

The current exercise and grammar result help the next step in this lesson thread. The language preference can tailor code examples months later. A raw transcript may support audit or reprocessing, but it should not be injected wholesale. Retrieve the stable preference by key and include it only when the current task involves code.

A claim such as “the learner struggles with the past tense” needs more care. That is an inferred profile, not a user-stated fact. Store evidence and confidence, require repeated observations, and let newer evidence replace it. In a fintech system, add tenant isolation, retention, deletion, audit, and protection against memory poisoning before calling the feature complete.

Reveal a model answer and self-check

Short-term memory is state scoped to one run or conversation thread, such as messages, tool results, and the current plan. It may be durable if a checkpointer saves it, so short-term does not mean in-memory. Long-term memory holds selected information that should be available across threads, such as user preferences or prior outcomes. The model can use neither store directly; the host must select or retrieve information and place it inside the context window for each inference.
